# Руководство по разработке Monitoring Service

## Область действия и источники истины

Эти инструкции применяются только к каталогу `monitoring-service/`. Назначение сервиса, границы ответственности, потоки событий и локальный запуск описаны в `MONITORING.md`. Реализованный контракт базы данных определяется моделями SQLAlchemy и зафиксированными миграциями Alembic. Не изменяйте уже применённую миграцию для изменения схемы — создавайте новую ревизию.

## Архитектурные правила

- Оставляйте FastAPI routers тонкими. Бизнес-решения и управление транзакциями размещайте в Service Layer, запросы к данным — в Repository Layer.
- Используйте Dependency Injection и зависимости от абстракций на границах слоёв. Не добавляйте абстракции без конкретного сценария использования.
- Работайте с базой асинхронно через `AsyncSession`. Не выполняйте блокирующий I/O внутри async endpoint или consumer.
- Monitoring владеет товарами, предложениями конкурентов, процессом сбора и историей цен. Не обращайтесь к базам других сервисов и не создавайте межсервисные внешние ключи.
- Взаимодействуйте с Collector и Pricing только через утверждённые HTTP- или RabbitMQ-контракты.

## Инварианты базы данных

- Используйте типизированные модели SQLAlchemy 2.x: `Mapped`, `mapped_column`, явную nullable-семантику, timezone-aware timestamps, UUID, нативные PostgreSQL ENUM и `Numeric(12, 2)` для денег.
- Каждая tenant-зависимая связь должна сохранять `organization_id` через существующий паттерн составных внешних ключей.
- Цена должна быть положительной. В наблюдении цена может быть `NULL` только одновременно с `NULL` в валюте.
- `Product.competitor_prices_version` начинается с `0`, а `CompetitorOffer.current_price_version` — с `1`. Увеличивайте версии атомарно внутри сервисной транзакции.
- Products, batches, jobs и observations являются историческими данными. Не добавляйте каскадное удаление без явной retention-политики. Отключайте предложения конкурентов через `is_active`, а не физическое удаление.
- Создание Inbox-записи и применение входящего бизнес-изменения выполняйте в одной транзакции. Outbox-событие создавайте в транзакции вместе с изменением агрегата.
- Сохраняйте `lazy="raise"`. Relationships загружайте явно в репозиториях, чтобы исключить скрытый async I/O и N+1.

## Миграции и проверки

Если не указано иначе, запускайте команды из `monitoring-service/`:

```powershell
uv sync
uv run mypy src
uv run pytest
uv run alembic check
```

Для изменения схемы:

```powershell
uv run alembic revision --autogenerate -m "описание изменения"
```

Проверяйте каждую сгенерированную миграцию вручную, особенно жизненный цикл ENUM, составные constraints, частичные индексы и порядок upgrade/downgrade. Применяйте миграции к PostgreSQL, а не SQLite. Из каталога `deploy/`:

```powershell
docker compose up -d monitoring-db
docker compose run --rm monitoring-migrate
```

Для изменённых CHECK, UNIQUE, FK, транзакционных и конкурентных инвариантов добавляйте integration-тесты с PostgreSQL. Не считайте миграцию готовой только на основании скомпилированного DDL или успешного `mypy`.

## Дисциплина изменений

Не выходите за границы Monitoring, если задача явно не включает общую инфраструктуру или межсервисные контракты. Сохраняйте чужие и несвязанные изменения. Перед добавлением таблицы, зависимости, кэша, worker или нового messaging-контракта объясните конкретную необходимость и компромиссы. Никогда не коммитьте секреты и реальные `.env`-файлы.
