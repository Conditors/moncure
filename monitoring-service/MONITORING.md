# Monitoring Service

Monitoring Service — центральный сервис товаров и мониторинга цен в Moncure.

Он управляет жизненным циклом собственного товара и предложения конкурента: от заявки на импорт до регулярных наблюдений и истории изменений.

## Ответственность

- собственные товары предпринимателя;
- источники собственных товаров;
- предложения конкурентов;
- подтверждённые связи между товарами;
- заявки и черновики импорта;
- ручное подтверждение импорта;
- ручные и плановые синхронизации;
- формирование заданий Collector;
- обработка результатов сбора;
- текущее состояние товара или предложения;
- история наблюдений цен;
- определение значимого изменения;
- запуск фонового пересчёта Pricing;
- агрегация результата синхронизации;
- подготовка одного сводного уведомления;
- базовые запросы истории и аналитики.

## Основные данные

Предполагаемые сущности:

- `Product`;
- `ProductSource`;
- `CompetitorOffer`;
- `ProductOfferMatch`;
- `ImportJob`;
- `ImportDraft`;
- `SyncJob`;
- `SyncJobItem`;
- `PriceObservation`;
- `CurrentOfferState`.

Точные модели и таблицы будут определяться отдельно при реализации соответствующего бизнес-сценария.

## Бизнес-инварианты

- товар не появляется в основном каталоге до подтверждения импорта;
- повторный результат Collector не создаёт второй черновик;
- повторное подтверждение не создаёт второй товар;
- одно предложение конкурента не связывается с товаром повторно;
- пользователь не видит данные другой организации;
- одна проверка источника не выполняется параллельно дважды;
- ошибка одного источника не останавливает общую синхронизацию;
- при отсутствии изменений не создаётся ложное событие изменения;
- время успешной проверки обновляется только после успешного результата.

## Взаимодействия

Frontend работает с Monitoring через API Gateway по HTTP.

Фоновый сбор:

```text
Monitoring -> RabbitMQ -> Collector
Collector -> RabbitMQ -> Monitoring
```

Фоновый пересчёт:

```text
Monitoring -> RabbitMQ -> Pricing
Pricing -> RabbitMQ -> Monitoring
```

Точные HTTP routes, exchanges, queues и routing keys будут определены вместе с контрактами соответствующих сценариев.

## История и аналитика

Monitoring владеет фактическими наблюдениями цен. В MVP отдельный Analytics Service не создаётся.

Сервис предоставляет историю, фильтрацию по периоду и простые агрегаты. Тяжёлая аналитика и отдельное аналитическое хранилище могут появиться позже только при подтверждённой необходимости.

## Планировщик и уведомления

APScheduler запускает ежедневную синхронизацию в фиксированное время. Ручная проверка не сдвигает следующее плановое выполнение.

Notification Worker отправляет одно итоговое уведомление после завершения всех проверок и необходимых пересчётов, а не отдельное сообщение на каждый товар.

## Надёжность

- сохранение бизнес-изменения и исходящего сообщения должно быть атомарным через outbox или эквивалентный механизм;
- consumers обрабатывают повторную доставку идемпотентно;
- сообщения содержат `message_id` и `correlation_id`;
- конкурентные подтверждения и запуски защищаются ограничениями PostgreSQL;
- Redis-lock не используется как единственная защита бизнес-инварианта.
