# Pricing Service

Pricing Service хранит экономические параметры товара и формирует объяснимые рекомендации по цене.

Сервис не обещает максимальную прибыль и не изменяет цену автоматически. Он рассчитывает допустимый ценовой порог и объясняет предпринимателю ограничения.

## Ответственность

- закупочная стоимость;
- дополнительные расходы на единицу;
- процентные комиссии;
- распределённые постоянные расходы;
- целевая прибыль;
- стратегия ценообразования;
- минимальная допустимая цена;
- рекомендация и объяснение расчёта;
- версия настроек и входных данных;
- фоновый пересчёт после изменения рыночных данных.

## Базовая модель расчёта

```text
min_price =
    (variable_costs + allocated_fixed_costs + target_profit)
    / (1 - percent_fees)
```

Формула является упрощённой экономической моделью. Налоги и сложные финансовые правила должны добавляться отдельно после проверки бизнес-требований.

Если цена конкурента ниже допустимого порога, сервис должен вернуть объяснимое предупреждение, а не рекомендовать убыточное снижение.

## Данные сервиса

Предполагаемые сущности:

- `PricingSettings`;
- `PricingSettingsVersion`;
- `PricingRecommendation`;
- `RecommendationInputSnapshot`;
- `PricingStrategy`.

Каждая рекомендация должна сохранять версию настроек, использованные наблюдения, алгоритм и время расчёта. Это позволяет объяснить и воспроизвести результат.

## Границы

Pricing Service не должен:

- быть источником истины о товарах;
- собирать данные с внешних сайтов;
- хранить полную историю цен;
- изменять таблицы Monitoring;
- автоматически менять цену в магазине;
- отправлять внешние уведомления.

## Взаимодействия

Frontend работает с Pricing через API Gateway по HTTP.

Для интерактивного расчёта Pricing получает актуальный снимок рынка из Monitoring через внутренний HTTP-контракт.

Для фонового расчёта Monitoring отправляет команду через RabbitMQ. Pricing возвращает результат, связанный с конкретным товаром и запуском синхронизации.

## Деньги и точность

- в Python используется `Decimal`, а не `float`;
- в PostgreSQL используется `NUMERIC`;
- правило округления задаётся явно;
- комиссия должна быть меньше 100%;
- денежные значения валидируются как неотрицательные;
- в первом MVP используется одна согласованная валюта.

## Надёжность

- повторная команда не создаёт дублирующую рекомендацию;
- старая команда не перезаписывает расчёт по более новым данным;
- идемпотентность учитывает товар, версию настроек и версию рыночного снимка;
- недоступность Monitoring обрабатывается как интеграционная ошибка, а не как нулевая цена.

## Тестирование

- unit-тесты формулы, комиссий и округления;
- тесты цены конкурента ниже безопасного порога;
- тесты отсутствующих или устаревших наблюдений;
- integration-тесты PostgreSQL и RabbitMQ;
- тесты идемпотентного пересчёта;
- API-тесты сохранения настроек и получения рекомендации.
